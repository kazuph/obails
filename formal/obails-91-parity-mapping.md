# Obails 91 parity: Quint translation map

This document preserves the pre-repair implementation in a separate historical-current model, which is expected to produce RED counterexamples. The repaired model is the candidate contract from `.codex/obails-91-parity-rules.md`. The current product working tree is checked against the repaired model's source anchors by `scripts/dspec/check-obails-parity-spec.mjs`; the preserved historical model is never overwritten with those anchors.

## Guard/action boundary notes

- `debounce` scheduling, switching, and the eventual save are separate actions. Combining them would erase the known race.
- External validation, a post-validation modify/delete/rename, and commit/reject are distinct actions. The repaired candidate rechecks at its abstract commit boundary; its successful conflict witnesses prove that the reject branch is reachable.
- Link forward-index export, concurrent rebuild publication, and target resolution are separate actions because `GraphService.GetFullGraph` releases the index lock between export and each `ResolveLink` call.
- Task scan/reference issuance, validation, post-validation external mutation, and commit are separate actions. This exposes the read/validate-to-`WriteFile` window that disappears when validation and commit are modeled atomically.
- The repaired commit action remains enabled after the post-validation mutation and takes an explicit rejection branch. The current `commitTaskReference` uses the equivalent `SaveIfUnchanged` commit boundary. Its `wrongTaskUpdated` predicate is derived from `taskWriteCommitted and taskTargetChangedAfterValidation`; `taskReferenceTargetsSameTask` therefore covers a reachable conflicting commit attempt rather than a state flag that no action can set.
- P-016 adds `current-post-validation-task-overwrite.itf.json` (RED) and `repaired-post-validation-task-rejected.itf.json` (expected reachability witness); both use distinct validation, mutation, and commit actions.
- `SaveIfUnchanged` performs a final `os.Stat`/`os.ReadFile`/`os.Stat` comparison at `services/file_service.go:208-243`, then calls `os.Rename` at line 244. A non-cooperating external writer can still change the destination after that final recheck and before `os.Rename`; `writeMu` coordinates only Obails writers. The candidate repaired GREEN does **not** prove this OS-level window closed in the current Go implementation.
- Workspace actions model one persisted record and one native tracker. They prove neither native-window callback ordering nor cross-process duplicate creation.
- The dedicated popout-route model separates live child mutation, rejoin, and stale mutation. Its repaired invariant proves only that the modeled exact-record guard preserves the main active pane and rejects a post-rejoin call; it does not prove browser/native window shutdown timing.

## Result interpretation boundary

The models cover bounded ordering and generation safety only. GREEN in the repaired model means the candidate guards are internally consistent for the modeled dimensions. In particular, the external-save candidate is not proof that the final-recheck-to-`os.Rename` non-cooperating-writer window is closed. The repaired-product anchors prove that named source connections exist in this working tree, not production implementation, UI conflict recovery, filesystem durability, parser parity, native-window behavior, live application behavior, or the other 91-item workstreams.
